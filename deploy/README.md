# Independent frontend and backend

Topology:

- `https://letmeknow.dev`: the complete GitHub-built static distribution on GitHub Pages. HTML, JS, WASM, fonts, icons, manifest and service worker come from this origin. Invite `/i` has its own static entry, including Pages' `/i/` redirect.
- `https://relay.letmeknow.dev`: VPS membership/iroh relay only. A `129.212.227.207`, AAAA `2400:6180:0:d2:0:3:37cd:7000`, DNS-only; the owner has created these records. Keep TCP 22/80/443 and UDP 7842/7843 open. TLS is issued independently for the relay name.
- No deployment, DNS, GitHub Pages or npm credentials belong on the VPS. The backend never serves the application, JavaScript configuration, or `/membership` discovery. `/`, `/i`, `/app.js`, `/sw.js` and `/membership` return 404.

## Release gates

`web/backend.json` names the 0.16 authority's PUBLIC key, `7fdc5178ea2da4c7c282d34dd183e6fb109e8afdcb61ffd3f1a9a7c715e50518`, provisioned with `serve --initialize` on the VPS (step 4); native clients default to the same key and to `https://relay.letmeknow.dev` (`crates/proto/src/links.rs`). Production builds fail without a 64-character hex key. Never put a private key or Spaces credentials in the repo, build environment, artifacts or logs.

The backend's `/stats` reports sitewide totals per completed UTC day; no statistics UI is provided.

`.github/workflows/release.yml` runs all-platform CI alongside five native platform builds. The Linux x64 release executable runs native E2E before packaging. A separate job builds the production frontend once from checked-in `backend.json`, typechecks it, and smoke-tests that exact directory (healthy welcome controls online, after service-worker control and offline) without contacting production. Malformed-Wasm and caught-startup-failure copies must fail the same gate. A separate inherited-worker/cache/settings scenario exercises browser-controlled recovery while preserving client IndexedDB. Full browser/native E2E uses a test-key build against a real local backend at a different HTTPS origin; it is not byte-identical to the production-configured build.

Native archives and the frontend carry the same normalized public `backend.json`, generated with the same loader as the compiled browser defaults. This file is artifact metadata, not runtime backend discovery; only the public key and relay origin are emitted.

Publication waits for all those jobs. The GitHub release includes native archives, `frontend.tar.gz` and SHA256SUMS; Actions also retains the artifacts. npm publication/availability for the platform packages and CLI must complete before the release run succeeds. Provenance identifies the publishing workflow/source; it does not prove harmlessness or reproducibility. Checksums detect byte differences, not malicious releases from a trusted publisher.

`deploy/release.sh X.Y.Z <notes file>` tags/publishes and prints the rollout commands; it does **not** deploy. Both rollout paths verify the actual release workflow path/ID, completed successful push, repository, reviewed tag and full source SHA, including the current tag target; display names are not provenance. The resolved identity is printed for review. Do not move a tag after npm publication. A failed or partial publication cannot be rolled out by the scripts. Artifact retention matters: use a retained successful run, not a local rebuild.

## Reviewed cutover (operator only)

1. Review all security gates, the intended tag/commit and release artifacts. Confirm administrative access to frontend DNS, repository Pages settings and the `github-pages` environment. Configure Pages source **GitHub Actions**, custom domain `letmeknow.dev`, HTTPS enforcement, and required operator approval on `github-pages`. Review the dispatch workflow on `main`; no token is copied to the VPS. Set/verify GitHub's domain ownership TXT record before changing DNS. Keep that verification record.
2. Inventory the old installation before deleting anything. Record exact paths/object keys and versions, process/unit names and owners; the parent must review the final inventory. Expected candidates, not a deletion script:
   - Old letmeknow/Litestream processes and enabled units; `/etc/litestream.yml`, `/etc/systemd/system/litestream.service.d/credentials.conf`, any other replication/restore jobs.
   - `/var/lib/letmeknow/membership.db`, its `-wal` and `-shm` sidecars; old signing authority material at `/var/lib/letmeknow/membership.key` and operator-held/remote copies. Keep TLS/ACME material distinct from signing state.
   - Spaces bucket `letmeknow-litestream` in sgp1: all replica objects/versions for the old `letmeknow.dev/membership.db` prefix and old signing-key objects under `keys/`; inventory any other prefixes before assuming the list is complete. Revoke the old bucket access credential. Inspect metadata/listings, not secret contents.
   - Old `/usr/local/share/letmeknow/web` assets, temporary upload copies and obsolete serving/proxy units; diagnostic histories/logs that may contain capabilities, handled under the separate leak review.
   - Old browser tabs, installed PWAs and service workers, plus DNS caches. **Never erase client homes or IndexedDB as part of server cleanup.**
3. At the actual reviewed cutover, stop the old service, stop/disable Litestream and other restore/replication jobs, and carry out only the reviewed deletions. The owner approved deletion of the old server database and Litestream/Spaces backups, not broad path deletion or client erasure. Remove obsolete replica provisioning and credentials. No script here restores or deletes production data.
4. Provision the fresh 0.16 authority and empty store: as the service account, `letmeknow serve --initialize --domain relay.letmeknow.dev --state /var/lib/letmeknow`, where the state directory does not exist yet. It writes `membership.key`, `membership.db` and, last, `membership.ready`, prints `membership: <public key>@https://relay.letmeknow.dev`, and exits; an interrupted run is abandoned, not resumed. `serve` refuses state without `membership.ready` or of another store format. Do not pair an empty/old DB with the old signing key, or restore old signed history. Normal restarts use the same durable new state. Catastrophic loss means explicitly provisioning a fresh authority, publishing its new public key in a new trusted client release, and recreating affected groups/identities as necessary. Clients keep old local data/evidence; unavailability is not permission to erase it.
5. Before release, commit the fresh PUBLIC key to `web/backend.json` and coordinate native defaults. Review the key against the authority provisioned in step 4. Complete release tests/publication. Inspect the successful run with `gh run view <run-id>` (tag, SHA, all jobs and npm availability), not merely an uploaded artifact or green individual job.
6. On the operator's workstation, run `deploy/deploy.sh root@129.212.227.207 relay.letmeknow.dev spoj/letmeknow <run-id> <vX.Y.Z> <full-source-SHA>`. It downloads the successful run's Linux x64 archive and installs its executable and packaged systemd template; it does not compile or upload frontend files. It requires the service account and complete initialized state already provisioned, Litestream inactive/disabled, and the selected artifact's relay domain matching the installation domain. After restart, `deploy/check-backend.py` requires the backend's `/health` to report the tag's version and the artifact's public key. Failure exits nonzero even though installation may already have occurred; there is no automatic rollback or replacement authority. Allow TLS provisioning to finish and rerun the check before proceeding. Review startup logs without printing secrets. No automatic key copying, restore, swap setup, package install or backups occur.
7. Verify relay TLS and the independent backend before frontend rollout: `curl -i https://relay.letmeknow.dev/health` (version and public service key; a self-report that catches mistakes, not an attestation), and 404s at `/`, `/i`, `/app.js`, `/sw.js`, `/membership`. Verify IPv4 and IPv6 separately and cross-origin WSS with real clients.
8. Change **only the frontend** apex DNS to the records GitHub Pages currently specifies for this repository/custom domain; remove the old VPS apex A/AAAA, preserve mail/TXT and relay records. Verify the Pages DNS check, certificate and HTTPS enforcement; do not use a VPS proxy or VPS-provided HTML as an interim fallback. Then run `gh workflow run pages.yml --repo spoj/letmeknow -f release_run=<run-id> -f release_tag=<vX.Y.Z> -f release_sha=<full-source-SHA>` from `main` and approve the `github-pages` deployment after reviewing that same backend/frontend run, tag, SHA and pinned readiness evidence. Before approval, that workflow verifies release provenance, compares the two artifacts' public configuration, checks the backend's `/health` against it, and prints the result in its summary. It prepares the exact frontend and freezes the config in a separate immutable artifact ID. After approval, it rechecks provenance (including the current tag target) and the backend's `/health` against that same frozen config before deploying the prepared Pages artifact. A backend/key/version change or unavailable backend blocks rollout; no newly selected artifact or rebuild crosses the approval boundary. Coordinate DNS/certificate and deployment readiness; expect an outage rather than an unsafe fallback.
9. Fetch `/`, `/i/`, `/app.js`, `/sw.js` and referenced WASM from Pages; compare bytes with the selected artifact (allow HTTP content encoding). Inspect browser Network: all executable/static assets from the frontend, WSS only to the chosen backend, no `/membership` discovery. Test a fresh invite in a fresh profile and an installed PWA/previously open tab. Update uptime monitoring from old `letmeknow.dev/ping` to the separately reviewed relay health endpoint; Pages availability is a separate check. Confirm old serving/backup processes cannot restart and remote backup objects/credentials are gone per the inventory.

## Browser updates and self-hosting

The service worker caches the built app and normally offers **Reload** when an update waits. Waiting/reload is an update policy, not cryptographic pinning: the same-origin host, DNS and release administrators still control code, and the browser may activate a waiting worker after all old tabs close. Changing DNS does not revoke an old page, worker or HTTP cache installed by the former backend. Do not assume those installations or their Reload buttons are trustworthy. Prefer a fresh separate browser profile for the new distribution. For an existing profile, use browser-controlled tools to close old tabs/PWAs, unregister the old worker, clear that origin's Cache Storage and cached HTTP files, and fetch/verify the selected trusted artifact. Preserve IndexedDB and client homes: never use blanket “clear site data”. Review `lmk membership` and `lmk relay` explicitly, then reload before creating new groups; previous backend code could have written them, so their presence does not prove human choice. This establishes new execution trust, not recovery of secrets already compromised by old code. An incompatible old tab must be refused by the separately owned storage/protocol gates, not trusted to cooperate.

Self-hosting: run `letmeknow serve --initialize --domain relay.example.com --state /var/lib/letmeknow` once, then `letmeknow serve --domain relay.example.com --state /var/lib/letmeknow`, on the backend. Publish a separately built `web/dist` on a trusted static HTTPS host. Put that backend's PUBLIC key and HTTPS relay origin in a separate JSON file with the same fields as `web/backend.json`; build with `LMK_FRONTEND_CONFIG=/absolute/path/backend.json npm run build` in `web/`. `LMK_FRONTEND_OUT` selects a build output directory (it is replaced by the build). Set the frontend hostname in the static host's configuration; the distribution carries no project-specific `CNAME`. Serve `/i/index.html` as well as `/index.html`, with JS/WASM MIME types; never substitute backend responses for static files.

Existing explicit browser choice remains available: on the trusted frontend origin, set localStorage `lmk membership` to `<public-key>@https://relay.example.com` and optionally `lmk relay` to an HTTPS relay URL, then close other tabs and reload. This affects new groups/identities, not existing groups' authorities. Removing those settings explicitly selects the build defaults again. No network error triggers fallback, and no URL parameter/backend response overwrites that choice. Native clients use `listen --membership <address> --relay <url>` (or their environment variables).

## CORS versus WebSocket origins

All static requests and WASM loads are same-origin. The backend's `/ping` is a credential-free cross-origin relay probe and retains `Access-Control-Allow-Origin: *`; it is not live public statistics. No REST membership API/config discovery needs CORS. Membership and peer transport use iroh over cross-origin `wss://relay…/relay`, not WebRTC. WebSocket handshakes do not use Fetch CORS/preflight; the current iroh relay accepts independent browser origins, including self-hosted frontends, without cookies. Authentication is the iroh/protocol exchange, not an Origin allowlist or CORS header. Do not enable credentialed wildcard CORS or add backend-supplied script/config as a workaround.
